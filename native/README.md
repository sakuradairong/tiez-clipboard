# Windows native migration prototype

This Windows-first branch incrementally introduces a WinUI 3 host and a Tauri-free Rust core. The existing Tauri entry point remains available as the migration reference. This prototype uses an explicitly supplied, separate SQLite database; it does not discover, migrate, or open the installed application's data.

## Rust core

```powershell
cargo test --manifest-path native/core/Cargo.toml
cargo build --manifest-path native/core/Cargo.toml
```

The DLL is `native/core/target/debug/tiez_native_core.dll` on Windows. The settings snapshot supports language, color mode, deduplication, search visibility, persistence, file/rich-text capture, privacy matching, cleanup rules/policies, and persistent limits. Reads never save defaults. Capture is explicitly started by the host; guarded Ctrl+V paste is available, with end-to-end target-app acceptance pending.

The core owns one stoppable Windows clipboard listener and capture worker per open handle. Startup records the current sequence without importing the existing clipboard. The worker uses the shared production format probes and transformations, preserves whitespace/source metadata, deduplicates with rich-format identity, and publishes history revisions. Settings acknowledgement applies the accepted policy before returning. Session-only captures keep negative IDs; persistent promotion reports replacement IDs. Save, encryption and storage-limit eviction share a transaction; owned attachment cleanup occurs after commit. Status reports counts and error codes without clipboard bodies. Stop/close joins the worker before releasing history; a synchronous delayed-render provider can delay shutdown until its read returns.

## ABI v1

- `uint32_t tiez_core_abi_version(void)` returns `1`.
- `char* tiez_core_request(const uint8_t* request, size_t len)` accepts 1..65536 bytes of UTF-8 JSON and returns owned, NUL-terminated UTF-8 JSON.
- `void tiez_core_free(char* response)` frees each response exactly once; null is allowed. Never free a response with a different allocator or unload the DLL while it is in use.

The caller owns the request and keeps its bytes valid for the call. Results are either `{ "ok": true, "result": ... }` or `{ "ok": false, "error": { "code": "...", "message": "..." } }`. Calls are serialized and have no UI thread affinity. Rust panics inside dispatch become errors under the default unwind profile; process-fatal failures such as allocation failure are not recoverable. Do not set `panic=abort` if panic recovery is required.

Commands:

```json
{"op":"open","database_path":"C:\\absolute\\isolated\\probe.db"}
{"op":"snapshot","handle":1}
{"op":"update","handle":1,"expected_revision":0,"patch":{"app.language":"en"}}
{"op":"clipboard_copy","handle":1,"id":1,"plain_text":false,"allow_sensitive":false}
{"op":"capture_start","handle":1}
{"op":"capture_status","handle":1}
{"op":"capture_stop","handle":1}
{"op":"close","handle":1}
```

`open` requires an absolute path with an existing parent directory. It returns a numeric handle and a snapshot. Share that handle across windows; a second concurrent open is rejected. `update` returns `changed` and a snapshot. Accepted changes advance a durable revision in the same transaction as the values. Reads, invalid/stale requests, failed writes and no-op saves do not advance it. Consumers publish accepted snapshots to their views only when `changed` is true; no callback thread or polling loop is required. Unknown database rows are retained and never included in snapshots. `close` invalidates the handle; closing a settings window must not close the core shared by the main window.

## WinUI 3 host

This unpackaged Windows x64 prototype requires .NET 10 Desktop Runtime and Windows App Runtime 1.8 (or their SDK/development installations). It uses WinUI controls with no HTML renderer. Build Rust first, then:

```powershell
dotnet build native/managed/TieZ.WinUI/TieZ.WinUI.csproj
dotnet run --project native/managed/TieZ.WinUI
```

The main window opens one independent settings window. Repeated opens activate it; closing it releases its subscriptions, while the application keeps the shared core alive. Accepted saves update both windows; initialization/reopening never writes settings. When the native tray registers successfully, closing the main window hides it while the shared core keeps running; the explicit Exit button or tray Quit action closes settings and disposes the core. Without an available tray, closing the main window exits normally. Theme and search visibility affect the main view; language remains a stored configuration value pending full localization. Deduplication and capture policies are applied by the Rust worker. The main history workspace now supports native incremental browsing, search/type/exact-tag/pinned filters, original-text details, add/edit/pin/tags and confirmed single deletion. Ordinary runs start capture when the main view loads. Its command bar can pause/restart capture and displays counters/error codes. The ordinary settings window edits 12 supported values, including capture/persistence/privacy/limit, and opens a separate advanced window for the four privacy/cleanup rule settings; rejected saves preserve drafts, and returning to accepted values disables unnecessary saving. Full paste-method/policy parity, full localization, migration of existing settings and packaging remain future work.

Normal runs use `%LOCALAPPDATA%/TieZ.Native.Prototype/settings.db`, separate from installed TieZ. To run an actual window smoke check after building:

# Create the report's parent directory first if it does not exist.

## Core history API

ABI v1 now accepts the following operations in addition to settings. All use the same application-owned handle:

```json
{"op":"history_page","handle":1,"query":{"limit":50,"offset":0,"search":"中文"}}
{"op":"history_entry","handle":1,"id":1}
{"op":"history_add","handle":1,"content_type":"rich_text","content":" text ","html_content":"<b>text</b>","tags":[]}
{"op":"history_pin","handle":1,"id":1,"is_pinned":true}
{"op":"history_edit","handle":1,"id":1,"content":" revised "}
{"op":"history_tags","handle":1,"id":1,"tags":["work"]}
{"op":"history_delete","handle":1,"id":1}
{"op":"history_delete_many","handle":1,"ids":[1,-1],"expected_revision":3}
{"op":"history_clear_preview","handle":1}
{"op":"history_clear","handle":1,"expected_revision":4}
{"op":"history_changes","handle":1,"after_revision":0}
```

History revisions are per core lifetime and separate from settings revisions. A page contains summaries (preview at most 500 characters, no original HTML/body); fetch original content with `history_entry`. Database page limits are 1..200. Like the legacy list, the first page additionally includes all matching bounded session-only entries. Use the returned `next_offset` and `revision` as the next query's `offset` and `expected_revision`. A revision mismatch requires restarting at offset zero. Each filtered call scans at most 2,000 stored rows; an empty page with `has_more=true` is not the end. Query filters also include `content_type`, exact `tag`, `tag_only`, and `pinned_only`. Search includes decrypted content, source, tags and valid non-sensitive OCR/QR records; `%` and `_` are literal characters.

Manual entries are persisted as in the old manual-entry command. Rust `record_processed` accepts pipeline-processed entries and provides bounded negative-ID session storage; it does not implement OS capture, cleanup or deduplication. Pinning/tagging a session item returns its positive ID and `replaced_id`; failure preserves the old item. Mutations return IDs/revision and queue a bounded change record. Consumers behind the 128-record feed receive `resync_required`. Successful persisted changes set `persistent_sync_pending`; a sync worker is not integrated yet, so this never claims remote delivery.

Sensitive save/tag changes validate encryption and commit tags, encrypted fields and OCR cleanup atomically. Same-source DPAPI and portable behavior is retained. Native default and portable core test suites each currently pass 53 tests; storage source tests pass 39. Full format round-trip acceptance/paste, global-tag-management UI, global-tag APIs and network acceptance remain pending. Requests still have a 64 KiB cap; oversized edits/imports need a chunked transport before complete replacement. No actual user database has been opened.

## Asynchronous managed history client

The C# client now exposes typed history query/entry/mutation/change-feed methods. Invoke them from the client's owner thread, then await them; serialization snapshots inputs before yielding and native work runs off the UI thread behind one request gate. Settings operations and disposal use the same gate. Cancellation stops queued calls, while an accepted mutation reports its actual native result even if cancellation arrives later. Disposal cancels waiting work and waits for the in-flight native response to be copied/freed before closing the handle. Views must discard stale or cancelled read results and cancel their own requests when closing.

The real-DLL smoke program additionally covers history DTOs, pages, Unicode/CRLF/HTML preservation, pin/tags/rich-to-plain edit/delete, stale pages, literal search, change feed, cancellation during a save, 32 queued reads at disposal and immediate reopen. The separate WinUI smoke check validates the native history workspace; these suites validate the OS listener lifecycle but do not establish real-content clipboard capture or target-application paste compatibility.

## Native history workspace

The virtualized ListView loads revisioned 50-row pages and continues through bounded empty scan pages. Search waits 250 ms and pauses during TextBox composition; new filters cancel older reads and clear the previous selection/detail. The change feed refreshes an idle first page, while active browsing keeps its position and offers an explicit refresh. Changed rows are redacted until refreshed, and stale mutations are blocked. View disposal cancels timers/reads before application-owned core disposal.

Sensitive rows bind a placeholder rather than their body preview; details are fetched only after explicit reveal. Changing the selection, filtering or refreshing clears the reveal. Accepted saves reload the returned ID (including session promotion), failed saves retain the dialog draft, and deletion requires confirmation. Native TextBox normalizes displayed/editor line endings, so accepting an unchanged edit preserves the original native payload; surrounding whitespace is retained. Details display original text, bounded native static image previews and structured rich text/tables. File rendering, complex rich-layout fidelity, embedded media, animation playback and full format-specific paste acceptance remain separate migration items. Extended multi-selection supports revision-guarded deletion; other batch actions, global tag management, real IME input, accessibility and mixed-DPI acceptance are still pending.

## Windows platform services

`native/platform` introduces a Tauri-free Win32 notification service and compiles the production `win_clipboard.rs` format implementation directly. `ClipboardListener::start()` acknowledges successful class/window/listener registration before returning one owner and a bounded receiver. The message procedure only stores a sequence hint and tries to enqueue one wake-up; consumers must read formats on their own worker and verify sequence stability. Bursts coalesce without blocking the window procedure. Stop/Drop signal a kernel event, remove the listener, destroy the HWND, unregister its unique class and join its thread. The timeout fallback also observes stop requests if signalling fails.

## History copy and OS clipboard acceptance

`clipboard_copy` takes an existing history ID, `plain_text` and explicit `allow_sensitive` (both default false), plus an optional `expected_revision` for a known history snapshot (see Revision-bound clipboard copies below). Copy does not itself change history. WinUI enables copy only for a loaded, current detail; revealing a sensitive entry enables its explicit copy. Accepted requests finish even if a later cancellation arrives, using the same managed request gate.

## Target tracking and return focus

The core owns one foreground-event hook and one top-level destruction hook on a single joined thread. `target_start`, `target_status`, `target_stop` and `target_restore` share the existing handle. Start before activating the main window to observe the prior external foreground. Status contains running/starts/generation/has_target/application/last_error; application is an executable basename, never a window title. The WinUI main view shows the target and offers return-focus/restart actions. Closing/reopening settings does not restart tracking.

`target_restore` requires `expected_generation`. An opaque internal ticket binds HWND, PID, thread and process creation time. Destroy events retire the matching top-level target and advance its generation; child-control destruction is ignored. Identity and exact foreground are rechecked around restoration. Event delivery is asynchronous; these checks reduce stale-handle risk but cannot make Windows focus or HWND lifetime atomic. Restoration is attempted only when the target already has focus or this process owns the foreground, using ordinary SetForegroundWindow. Refused activation, stale/closed targets and other foreground owners return errors. There is no keyboard injection or clipboard access in return-focus.

## Guarded history paste

`clipboard_paste` accepts `handle`, `id`, `expected_generation`, `plain_text` and `allow_sensitive`. It prepares the authoritative history body with the same sensitive gate and format writer as copy, restores/verifies the target, then writes the prepared clipboard with sequence-bound capture echo. The pre-write guard runs under the capture gate. Immediately before input, it checks current modifier/V state, clipboard sequence and exact foreground/ticket identity. No UI body or arbitrary window handle is accepted. WinUI offers original-format/plain-text paste only for current loaded details and a running tracker with a known target.

The initial native input path sends one balanced Ctrl+V batch. If Ctrl/Shift/Alt/Win or V is held, it rejects without releasing those keys. A partial SendInput result triggers one reverse-order key-up cleanup for only the accepted pending keys, using the same pure accepted-key tracking rules as the legacy sender. No paste retry, forced modifier release, AttachThreadInput or elevation is attempted. Errors after writing explicitly identify clipboard mutation and accepted input/cleanup counts; history is retained. A complete four-event receipt means Windows accepted input, not that the target consumed the content. Foreground, keyboard and HWND lifetime are not atomic on Windows; changes after the final guard remain possible.

Platform tests use a fake sender for idle/focus/sequence rejection, balanced success, all partial prefixes, blocked input and incomplete cleanup; they never inject actual keys. Core default/portable suites each pass 47 cases, including rejection before clipboard commit; legacy tests pass 279. The real-DLL smoke rejects stale/stopped paste requests before any OS mutation. The previous 47-phase WinUI check covers disabled paste with no detail or stopped tracking, restart through the actual button, and no WebView2 load. It does not exercise successful paste. ## Native tray and resident lifecycle

The core now owns one `ShellService` thread with a hidden top-level native window, a tray icon and a bounded ordered queue of host actions. `shell_start` requires `show_tray` (true for the WinUI host, false for headless message checks); repeating identical startup is idempotent, while changing live options requires stop/restart. `shell_poll` returns `{status, actions}` with `running`, `starts`, `tray_visible`, `last_error` and show_main/open_settings/quit/toggle_main actions. Quit takes priority over other pending actions. `shell_stop` and core close join the thread, remove its icon and destroy its window/class/resources. Popup shutdown requests EndMenu on the owner thread; an open-menu shutdown has not yet been exercised.

Tray v4 selection (mouse release or keyboard selection) requests showing the main window. Its context menu offers show/settings/quit. WinUI dispatches these actions with a separate timer, independently of history selection/loading and settings dialogs. Main-window close cancels the native close request only while the tray is available; capture and settings ownership survive hiding. Settings can open and close independently while main is hidden. Explicit Exit closes all windows/core. The tray icon is extracted from the host executable, whose ApplicationIcon now uses the existing TieZ ICO, with a shared system-icon fallback if extraction fails.

The hidden top-level window handles Explorer's TaskbarCreated message by re-registering the icon. If registration later fails, host polling reveals a hidden main window and disables close-to-tray. Startup failures keep the main window accessible and report the failure. Actual Explorer restart/recovery, popup selection/keyboard accessibility and physical tray clicks remain unverified; no Explorer process or user clipboard was changed for these checks.

## Main-window keyboard shortcut and transactional settings

The fifteenth native setting is the existing `app.hotkey`, retaining the legacy `Win+V` default. Normal startup attempts registration on the Rust shell owner thread with MOD_NOREPEAT. Windows/system/other-app conflicts report hotkey_error while keeping the tray and main-window recovery path. No registry policy is changed to take over Win+V. An empty value disables the binding. Keyboard aliases, letters/digits, F1–F24, numpad keys and common navigation/OEM names are supported. MouseMiddle/MButton values can still be read, but saving them to the live native host reports hotkey_mouse_pending; mouse hooks and the other search/paste/relay/queue keys remain required migration work.

The shell accepts provisional bindings through an eight-slot command channel. A new chord registers while the old binding is retained. Settings validates revisions and writes under its SQLite transaction, then prepares the native change before COMMIT. Failed preparation rolls back SQLite; failed COMMIT drops the provisional registration and retains the prior binding. No-op/stale saves do not prepare effects. After a durable commit, native finalization replaces/disables the old binding. An old-binding cleanup failure leaves the accepted snapshot explicit via side_effect_error, LastSideEffectError and the settings warning; it is not reported as an unsaved draft. Remaining stale registrations do not dispatch and block further hotkey changes until restart. Stop/Drop releases the bindings/window.

WM_HOTKEY must match the current non-reused registration ID, modifiers and key. Provisional, rolled-back, mismatched and disabled IDs are ignored. Host actions now use an ordered 32-slot queue: only adjacent idempotent show/settings duplicates coalesce; toggle counts/order are preserved, quit wins and overflow is reported. WinUI shows/activates the window when hidden/unfocused and hides a focused main window when the tray remains available. Settings expose accepted values and retain rejected/conflicting drafts. `shell_start` additionally accepts bind_main_hotkey (default true); smoke startup passes false to avoid automatically registering the user's system key.

## Native multi-selection and atomic deletion

The WinUI history ListView now uses Extended selection (Ctrl/Shift selection). Deleting one or multiple selected entries requires the native confirmation dialog, whose default is Cancel. Explicitly selected pinned/tagged entries are included, and the confirmation says so. Multi-selection clears single-entry detail/reveal state and disables copy/paste/edit/pin/tag actions. Search and exact-tag text invalidate the entire selection synchronously with TextChanging while preserving the query debounce and composition guards. Physical IME/keyboard/accessibility acceptance remains pending.

`history_delete_many` / `DeleteEntriesAsync` accepts 0–1000 explicit nonzero IDs and a required expected history revision. Empty selection is a no-op; duplicate IDs are coalesced. Missing IDs, stale revisions, oversized/invalid selections, SQLite deletion errors and failed COMMIT preserve stored/session entries, revision and change feed. The whole selection produces one revision and one removed_ids event. Persistent deletions use the same tombstone/tag maintenance as the existing repository.
